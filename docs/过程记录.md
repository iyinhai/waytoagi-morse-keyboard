# 摩斯电码练习机 —— 从网页到板子的完整过程

> WaytoAGI 第七期 AI 硬件训练营 · 第 8 课作业
> 完成时间：2026-10-27
> 硬件：EasyInput V2（ESP32-S3R8 / 16MB Flash / 8MB Octal PSRAM）

---

## 一、目标

做了两个东西，一个软的、一个硬的：

1. **摩斯电码练习机网页**——在浏览器里练摩斯码，出题、判对错、算分数、能自动校准手速
2. **把板子变成摩斯发报键**——板上 KEY1 按下就发空格，配合网页，按住时间长短就是点和划

第 2 条才是真难点：板子出厂是语音助手（按住说话、连 Wi-Fi、走 Codex 语音），要把它改成纯键盘输入设备。

---

## 二、为什么选这个方案

**为什么是摩斯电码？** 它天然适合"只有几个按键"的硬件。不需要键盘阵列，一个键 + 时间长短就能表达全部字符。而且有个硬约束逼着把交互做对：**点划靠时长区分，人跟人的手速差异极大**，所以必须有校准，不能写死阈值。

**为什么网页 + 板子而不是纯网页？** 纯网页点鼠标也能练，但那就没有硬件课的意义了。板子的价值是手感——真实发报键的物理反馈，鼠标给不了。

**为什么改固件而不是在中间件里转换？** 一开始想的是在 Mac 上跑个程序，读板子的语音按键事件再转成空格。但那样必须常驻后台进程，拔了电脑就不能用，而且延迟不可控。直接改固件，板子就是一个标准 BLE/USB 键盘，插哪台电脑都能用，不需要任何驱动。

## 三、摩斯练习机网页

单个 HTML 文件，20,763 字符，零依赖，双击就能开。

### 核心逻辑

- **点划判定**：按住时长 < `dotMax`（默认 200ms）记为点，否则记为划
- **两级断字**：字母内间隔超过 `letterGap`（600ms）就提交当前字母；超过 `wordGap`（1600ms）算词结束
- **摩斯表**：48 条目，A–Z、0–9、常用标点，逐条跟标准码比对过，无重复映射
- **自动校准**：连收 5 个样本，取平均 × 2.2 作为新阈值，限制在 80–400ms 之间
- **即时判错**：每提交一个字母立刻比对目标词对应位置，错字当场变红并提示正确码

### 测试怎么做的

没有用浏览器自动化，而是**自己搭了一个最小 DOM 桩 + 假时钟**，把页面里的真实脚本 `eval` 出来跑：

- 断言 21 项，覆盖 SOS 解码、点划阈值分界（195ms 判点 / 205ms 判划）、Tab 换词、Enter 提交、Backspace 删字、错字即时标红、自动校准
- 全部通过

### 测出来并修掉的 3 个真实 bug

| 问题 | 现象 | 修法 |
|---|---|---|
| 答对后 700ms 就换词 | 用户看不清自己刚敲的 | 改成 1600ms，并加 `awardedFor` 防止同一词重复加分 |
| 答错要等整词敲完才提示 | 反馈太晚，练不出手感 | 新增 `checkLetter(ch, idx)`，逐字母即时判 |
| 状态字段未声明 | `rebinding`、`calCount`、`calKey` 缺失 | 补全字段定义 |

> 这里有个值得记的教训：第一次跑测试只过 3/9，我以为是断字逻辑坏了。实际是**测试脚本自己写错**——我用 700ms 间隔敲点划，超过了 600ms 的 `letterGap`，每个点都被正确断成了独立字母。改测试用 400ms 后，11/18 通过，剩下的 3 个才是真 bug。**测试失败先怀疑测试本身。**

## 四、板子改造

### 4.1 板子是什么

| 项 | 值 |
|---|---|
| 芯片 | ESP32-S3R8，8MB Octal PSRAM |
| Flash | 16MB |
| MAC | `c4:9e:7e:07:a0:30` |
| BLE MAC | `C4:9E:7E:07:A0:32` |
| USB | VID `0x303A` / PID `0x1006`，TinyUSB HID 复合设备 |

走 USB 时是个复合 HID 设备，包含 4 个集合：

| usage_page | usage | 用途 | report id |
|---|---|---|---|
| `0x0001` | `0x0006` | 键盘 | `0x01`，8 字节载荷 |
| `0x0001` | `0x0002` | 鼠标 | `0x02` |
| `0x0001` | `0x0001` | 指针 | — |
| `0xFF00` | `0x0002` | 厂商配置通道 | `0x10`–`0x15` |

配置下发走厂商通道的 **feature report `0x10`**：64 字节分块、最大 2048 字节、CRC16 校验。状态上报走 **input report `0x11`**，格式是分片 JSON（14 字节帧头 + 50 字节负载）。

### 4.2 改了什么

一共三处，按重要性排：

#### ① 根因修复：让按键绕过 Codex 语音槽位机

**这是整件事最关键的一处。** `firmware/main/app_main.cpp` 的 `handle_input_event()` 里：

```cpp
if (is_codex_slot_input(event.input)) {   // KEY1..KEY8 全部命中
  handle_codex_slot_transition(app, app->codex_slots.handle_input(...));
  return;                                 // ← 直接 return，键位表永远走不到
}
```

KEY1–KEY8 被无条件交给 Codex 语音槽位状态机，然后 `return`。而 `CodexSlotState::handle_input()` 在 `connection_generation == 0` 时（纯键盘场景：没配 Wi-Fi、没有 audio host），对每个按下的键只回一个 `DeviceActionKind::RejectedBusy`——只打一条 `ESP_LOGW`，什么也不做。

所以现象是：**按 KEY1 灯会变红，但一个键码都不发**。灯亮是按键反馈（`input_feedback.cpp` 里 KEY1 的反馈色就是 `{28,0,0}`），跟动作解析完全无关，这点特别容易误判。

修法是给这个分支加条件——只有真连上语音路由时才交给槽位机：

```cpp
const bool codex_owns_keys =
    app->codex_route_generation != 0 || app->codex_slots.capture_active();
if (is_codex_slot_input(event.input) && codex_owns_keys) {
  handle_codex_slot_transition(app, app->codex_slots.handle_input(...));
  return;
}
```

这样纯键盘场景下按键老老实实走 `config_state.keymap()`，连上 Wi-Fi 后语音功能照常。

#### ② 固件默认键位改成摩斯键位

`firmware/components/keyboard/src/keymap.cpp` 新增 `MorseKeymap()`，并让 `DefaultKeymap()` 返回它：

| 键 | 动作 | HID 键码 |
|---|---|---|
| KEY1 | 空格（发报） | `0x2C` |
| KEY2 | 关闭（防误触打出回车） | — |
| KEY3 | Tab（换词） | `0x2B` |
| KEY4 | Backspace（删字） | `0x2A` |
| KEY5 | Enter（提交） | `0x28` |
| KEY6–8 | 关闭 | — |
| 旋钮三向 | 关闭 | — |

同时保留 `UpstreamDefaultKeymap()`（课程原始出厂键位：语音键 + 语义快捷键），方便对照和回退。改 `DefaultKeymap()` 只需要改一行 `return`。

#### ③ host 工具加离线配置模式

板子的 `audio_enabled` 是**推导值**，不是开关：

```cpp
// config_state.cpp
bool audio_enabled() const {
  return !wifi_ssid.empty() && !audio_host.empty() && port in 1024..=65535;
}
```

所以空 ssid + 空 host 就是合法的"纯键盘"态，不需要假装禁用语音。基于这一点给 `LanProvisioning` 加了 `offline()` 构造器，下发键位时不用再问 Wi-Fi 密码。

> 有个小坑：`audio_port` 仍必须给合法值（`1024..=65535`），写 0 会让整份配置被判为 `InvalidJson`。所以离线模式下端口保留默认的 17333。

### 4.3 键位怎么下发

配置不写死在固件里，而是走 NVS。所以改键位不用重新编译：

```bash
# 只看要下发什么，不碰板子
easy-codex-host provision-lan --offline --scene morse --preview

# 真正写入
easy-codex-host provision-lan --offline --scene morse
```

下发成功返回：

```
status=provisioned transport=usb_hid payload_bytes=627 chunks=13 crc16=822
```

`morse.json` 场景定义：

```json
{
  "id": "morse", "name": "摩斯电码",
  "keys": {
    "KEY1": "hotkey:space", "KEY2": "disabled",
    "KEY3": "hotkey:tab",   "KEY4": "hotkey:backspace",
    "KEY5": "hotkey:enter", "KEY6": "disabled",
    "KEY7": "disabled",     "KEY8": "disabled"
  },
  "encoder": { "left": "disabled", "right": "disabled", "press": "disabled" }
}
```

## 五、踩过的坑（这部分可能比结论有用）

### 坑 1：ESP-IDF 环境找不到 `idf5.5_py3.13_env`

`source export.sh` 报 `idf5.5_py3.13_env not found`。原因是 PATH 上有个 Python 3.13 抢在前面，IDF 按它去算虚拟环境名。

**修法**：先把真正的 venv 顶到 PATH 最前面再 source。

```bash
export PATH="$HOME/.espressif/python_env/idf5.5_py3.14_env/bin:$PATH"
source "$IDF_PATH/export.sh"
```

### 坑 2：官方固件的 ACK 格式跟 host 工具不兼容

下发配置一直报 `HidAck` 超时。用 `hid-watch` 抓报文才发现：**板子其实在正常回 ACK**，只不过格式是分片 JSON（`config_status.v1`，里面写 `bytes: 914, crc16: 48061`），而 host 的 `decode_config_ack` 期待的是单帧 `phase/ok/saved/bytes/crc16`。

这是官方固件 0.5.16 和本地 host 工具的版本错配。换成自家编译的固件后，ACK 一次通过。

### 坑 3：刷完固件板子卡在下载模式

刷完必然出现：

```
rst:0x15 USB_UART_CHIP_RESET, boot:0x3 (DOWNLOAD)
waiting for download
```

试过全部无效：DTR/RTS 手写时序（4 组）、`--after hard_reset`、`--after no_reset run`。

**有效的是 `--after watchdog_reset`**：

```bash
esptool --chip esp32s3 -p /dev/cu.usbmodem3101 \
  --before no_reset --after watchdog_reset run
```

原因：走 USB 触发的复位会被 ROM 判定为"要下载"，而走 RTC 看门狗复位不经过 USB 路径，芯片正常从 flash 启动。一次成功，串口消失、HID 集合从 4 变 8（USB + BLE 各 4 个）。

> 这条已经写进 `firmware/flash-morse.sh`，以后刷写能一条命令闭环，不用再物理拔线。

### 坑 4：拔插 USB 也没用——因为板子有电池

以为"拔掉 USB 就会断电重启"，结果拔了再插还是下载模式。

真正原因：**板子带电池，拔掉 USB 后芯片一直由电池供电，根本没断电**，所以只是 USB PHY 重新枚举了一次，芯片仍停在 ROM 下载模式。

### 坑 5：擦 NVS 把蓝牙配对一起清了

`CONFIG_BT_NIMBLE_NVS_PERSIST=y`，蓝牙配对密钥和键位配置都存在 `0x9000` 的 nvs 分区。当时为了修蓝牙去擦 `0x9000`，结果两边一起没了，得重新配对。

现在 `flash-morse.sh` 刻意**只写 bootloader + 分区表 + 应用，不碰 0x9000**，刷固件不会伤到配对和配置。

### 坑 6：`hid-watch` 根本看不到键盘报文（假阴性，害人最深）

用 `hid-watch` 监听 90 秒，一条键盘报文都没有，于是判断"板子没发"。**这个判断是错的。**

macOS 对键盘集合有**输入保护**：厂商通道（report `0x11`，64 字节）读得到，标准键盘报文（report `0x01`，9 字节）即使 `open_device` 成功，非受信任进程也收不到 input report。

所以「hid-watch 读到 0 帧键盘报文」**不能**作为板子没发报文的证据。唯一可信的判据是：**在真实应用里有没有打出字符**。

### 坑 7：我自己写的两个判据 bug

在一个本来就已经不可靠的观测手段上，我还加了两个错判据：

1. 过滤写成 `usage_page=0x0006`，实际标签是 `usage_page=0x0001 usage=0x0006` → 全部漏判
2. 用「报文里出现 `2C`」判空格 → 厂商 JSON 报文里的**逗号正好就是 `0x2C`**，必然误报成功

正确判据必须是：`bs[0] == "01" and len(bs) == 9`，然后在键位字节（第 4 字节起）里找 `2C`。

两个 bug 都已修进 `firmware/verify-morse.py`，并且在抓不到时明确提示"不可据此判断"。

### 板上配置指纹为什么重要

板上状态报文里会回 `bytes` 和 `crc16` 两个字段，描述的是**当前生效的那份配置**。拿它跟 host 端算出来的值对比，就能在完全不依赖固件日志的情况下，确认板上跑的到底是不是你想要的那份键位。

本次两边都是 `627 / 822`，所以板上确实是 morse 场景，`KEY1 = {"press":{"hotkey":"space"}}`。

## 七、遗留问题

1. **KEY3/KEY4/KEY5 没有逐键验证** —— 受坑 6 限制，本机无法可靠观测键盘报文。理论上走的是同一套 keymap（`default_eight_keys_emit_exact_hid_for_both_platforms` 测试覆盖了四个键的精确 HID 码），但真机没逐个按过。
2. **语音功能会抢占按键** —— 连上 Wi-Fi、audio host 可用后，KEY1–KEY8 会重新交给 Codex 语音槽位机。这是设计如此（语音是这块板子的原生用途），但如果要用摩斯就不要连 Wi-Fi。
3. **`--after watchdog_reset` 是实用解不是官方文档解** —— 对 ESP32-S3 + TinyUSB 的组合有效，换芯片型号需要重新验证。

## 九、一句话回顾

这件事看起来是"给板子换个键位"，实际卡住的地方全在**看不见的地方**：按键被上层状态机吞掉、刷完固件起不来、唯一的观测手段是个假阴性。真正修好只用了 12 行代码，但找到这 12 行花了很久——因为中间每一个"证据"都得先验证它是不是真的。
